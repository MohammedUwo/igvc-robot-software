# IGVC Dynamic AutoNav Course Generator

This repo generates seeded IGVC-style AutoNav Gazebo worlds. The current generator uses a modular grid/tile lane system: each grid cell contains one prevalidated tile with local lane geometry, connection metadata, and spawn permissions. Course topology comes from the tile graph; randomization is kept to obstacle placement and visual/environmental variation.

## What it creates

Each run produces:

```text
generated/generated_world_<seed>.sdf
generated/generated_course_<seed>.yaml
generated/generated_course_<seed>.png
generated/debug/generated_layout.json
generated/debug/generated_layout.png
```

The SDF contains white lane marking strips as compact visual links named `lane_segment_####` inside one `lane_markings` model, obstacle models, ramp geometry when allowed, and the asphalt platform. The compact lane batching keeps Gazebo load time down by avoiding hundreds of separate lane models. The YAML contains the selected tile template, transformed tile instances, lane boundary polylines, lane rendering stats, obstacle positions, ramp metadata, and validation flags. The debug JSON/PNG are intended for inspecting grid topology, tile names, entry/exit arrows, lane boundaries, obstacles, and ramp placement.

## Modular tile system

The lane generator no longer builds a global random polyline. It uses this pipeline:

1. Load `config/tile_library.yaml`.
2. Load a route from `config/course_templates.yaml`.
3. Place each tile on the grid using `pos: [i, j]` and `rotation_deg`.
4. Generate the tile's local lane boundaries from its local centerline.
5. Transform local tile geometry into world coordinates.
6. Export lane segments as SDF visual strips.
7. Place obstacles only in tiles that allow them.
8. Validate the route and write debug artifacts.

This keeps geometry local and predictable, preventing accidental cross-course line jumps and global lane overlaps.

Current IGVC-scale defaults:

```text
course_length_ft: 500 target, generated centerline within +/- 5 ft
operating_area: 120 ft wide x 100 ft deep
tile_size: 14.2 m
lane_width: 3.658 m / about 12 ft
track_width_ft: constrained to 10-20 ft
minimum_turn_radius_ft: 5
minimum_obstacle_line_clearance_ft: 5
minimum_passage_width_ft: 5
```

### Tile coordinates

Each tile uses local coordinates:

```text
tile center = (0, 0)
+X = east
+Y = north
tile spans from -tile_size/2 to +tile_size/2
```

World transform:

```text
world_point = tile_origin + rotate(local_point, tile_rotation)
```

### Tile library

Minimum useful tile set in `config/tile_library.yaml`:

```text
straight
gentle_left
gentle_right
hard_left
hard_right
s_chicane_left_right
s_chicane_right_left
lane_gap
no_mans_land_entry
no_mans_land_exit
no_lane_zone
ramp_straight
ramp_zone
obstacle_zone
```

Example tile shape:

```yaml
straight:
  entry_side: south
  exit_side: north
  entry_heading: north
  exit_heading: north
  centerline:
    - [0.0, -6.0]
    - [0.0, 6.0]
  allowed:
    cones: true
    potholes: true
    barricades: true
    ramp: false
```

Local lane boundaries are generated by offsetting the tile centerline by `lane_width / 2`. Tiles with `paint_lanes: false`, such as `no_lane_zone`, intentionally export no lane markings.

### Course templates

Templates declare the grid route. Example:

```yaml
templates:
  oval_with_chicane:
    grid:
      - tile: straight
        pos: [0, 0]
        rotation_deg: 0
      - tile: s_chicane_left_right
        pos: [0, 1]
        rotation_deg: 0
      - tile: hard_right
        pos: [0, 2]
        rotation_deg: 90
```

Each route entry stores:

```text
grid_position = [i, j]
rotation_deg = 0 / 90 / 180 / 270
tile = tile name from tile_library.yaml
```

## No Man's Land

No Man's Land is modeled with special tiles:

```text
no_mans_land_entry
no_lane_zone
no_mans_land_exit
```

`no_lane_zone` has no painted lane markings. Obstacles may still appear there if the tile's `allowed` settings permit them, and the route still provides centerline/waypoint continuity for navigation.

## Chicane

The S-curve chicane is a dedicated tile:

```text
s_chicane_left_right
s_chicane_right_left
```

Do not inject chicane control points into a global lane list. Edit the chicane tile's local centerline in `config/tile_library.yaml`, then run validation. The tile implementation samples the local centerline and offsets it locally to produce lane boundaries.

## Obstacle and ramp placement

Spawn rules live in:

```text
config/spawn_rules.yaml
```

Obstacle placement is separate from lane geometry. IGVC obstacles are generated as colored construction barrels/drums and 2 ft diameter potholes. Each tile controls whether obstacle placement or the ramp are allowed:

```yaml
allowed:
  cones: true      # legacy obstacle-capable flag; spawns barrels/drums
  potholes: true
  barricades: true # legacy obstacle-capable flag; spawns barrels/drums
  ramp: false
```

The ramp is a single explicit `ramp_tile_feature` and is only placed on one `ramp_straight` tile per course. That tile is a straight tile with `allowed.ramp: true`; generic `ramp_zone` tiles are kept as a non-spawning zone type. The ramp pose is anchored at the tile origin, aligns with the tile centerline, and inherits the tile rotation. A clearance rectangle around the ramp rejects barrels, drums, and potholes, and generated metadata records `ramp.clearance_passed` and `ramp.clearance_obstacle_count`. The generated SDF model is named `ramp_tile_feature_###` and includes visible `ramp_lane_left`, `ramp_lane_right`, and `ramp_centerline` markings on top of the ramp. Obstacles are not allowed within 5 ft of lane lines and are not allowed to fully block the chicane; metadata records minimum line clearance and passage width checks of at least 5 ft.

## Validate a generated course

```bash
python3 scripts/validate_course.py generated/generated_course_42.yaml
```

Important validation signals in the YAML:

```text
course.generation_mode: grid_tiles
course.validation.route_is_connected
course.validation.closed_loop_endpoints_match
course.validation.no_lane_zone_has_no_markings
course.validation.obstacles_do_not_block_chicane
course.validation.minimum_passage_width_ft
course.validation.ramp_not_inside_chicane
```

The generator fails loudly for invalid tile courses instead of exporting known-bad geometry.

## Launch with ROS 2 / Gazebo

World only, fixed seed:

```bash
cd /media/igvc/OS/dynamic_Gazebo_IGVC_Autonav_Course
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch igvc_sim sim_random.launch.py seed:=42 scenario:=normal
```

World only, random seed:

```bash
ros2 launch igvc_sim sim_random.launch.py scenario:=dense
```

The world-only launch file generates the world first, then starts Gazebo with the generated SDF.

### Launch generated world with the robot automatically spawned

Use this when you want the existing `diff_drive_robot` model to appear in the generated course without manually adding it each time. Source both workspaces before launching:

```bash
cd /media/igvc/OS/dynamic_Gazebo_IGVC_Autonav_Course
source /opt/ros/humble/setup.bash
source install/setup.bash
source /home/igvc/gz_ws/ros2_ws/install/setup.bash
ros2 launch igvc_sim sim_random_with_robot.launch.py seed:=42 scenario:=normal
```

`sim_random_with_robot.launch.py` does this pipeline:

```text
generate generated_world_<seed>.sdf
generate generated_course_<seed>.yaml
read the generated start pose from YAML
start Gazebo with the generated world
start robot_state_publisher using diff_drive_robot/urdf/robot_processed.urdf
spawn diff_bot at the generated start line with ros_gz_sim create
start the ROS-Gazebo bridge
```

By default it does not start controllers, lidar debugging, EKF, SLAM, or autonomy. That is intentional: first make robot spawning reliable, then debug controllers/sensors/autonomy separately.

Optional arguments:

```bash
ros2 launch igvc_sim sim_random_with_robot.launch.py seed:=42 scenario:=normal rviz:=True
ros2 launch igvc_sim sim_random_with_robot.launch.py seed:=42 scenario:=normal autonomy:=True
ros2 launch igvc_sim sim_random_with_robot.launch.py seed:=42 scenario:=normal spawn_z:=0.20
```

## Notes for editing

Keep generation deterministic for a fixed seed. Do not add timestamps, UUIDs, unordered output, or absolute machine-specific paths to metadata.

When changing lane geometry:

1. Edit local tile centerlines in `config/tile_library.yaml`.
2. Keep the route topology in `config/course_templates.yaml`.
3. Run tile tests.
4. Generate seed 42 and inspect `generated/debug/generated_layout.png`.
5. Run `gz sdf -k generated/generated_world_42.sdf`.

Generated files are intentionally ignored by Git except `generated/.gitkeep`.
